# DS Chiptune Tracker — Scope

A touch-first music tracker for iOS and iPadOS that sounds exactly like the Nintendo DS sound hardware and exports songs that play on a real DS.

*Scoped 2026-09-25. Working name TBD.*

## Decisions

| Question | Decision |
| --- | --- |
| Platform | iOS / iPadOS first. The audio core is portable C/C++ so it can later run on desktop and on the DS itself. |
| Accuracy | Hardware-accurate DS sound chip (SPU). Anything a song does must be possible on real hardware. |
| Editing style | LSDj/M8-style nested screens (song → chain → phrase), plus instrument, table and groove screens. |
| Export | WAV/M4A audio, a playable `.nds` ROM, and SSEQ/SDAT (Nintendo's sound format). |

## Why this is worth building

- **Furnace**, the biggest multi-system tracker, emulates the DS chip accurately but has *no driver to export to*, so its DS songs can't run on hardware. Real ROM and SSEQ export is an open gap.
- There's no good touch-first tracker for DS sound. LSDj and the M8 prove the nested-screen design works on small screens.
- It plays to your mobile skills, reuses what you learned building the Duo DS emulator, and SSEQ export leads straight into ROM hacking (replacing music in real games).

## The DS sound hardware (what we emulate)

Reference: GBATEK, the community's DS hardware documentation, sound section.

- **16 channels.** Every channel can play samples in PCM8, PCM16 or IMA-ADPCM format.
  - Channels 8–13 can also play **PSG square waves** with 8 duty settings (12.5% to 87.5% high, plus a constant low).
  - Channels 14–15 can also play **noise**, generated by a 15-bit shift register.
  - Channels 0–7 are sample-only.
- **Per-channel settings:** volume (0–127) with a divider (÷1, ÷2, ÷4 or ÷16), pan (0–127), a 16-bit pitch timer, sample looping (loop start and length, or one-shot), and hold.
- **Global settings:** master volume and 10-bit output at about 32,728.5 Hz (one sample every 1,024 ARM7 cycles).
- **2 capture units** record the output of channels 0 and 2 (or the mixer) back into memory. Games use them for reverb and feedback effects. This is a stretch goal.
- **No hardware envelopes, vibrato or effects.** Nintendo's sound driver on the DS's secondary ARM7 CPU does all of that in software. This means we control the software layer entirely, which is how we can support three export formats.

## Architecture

The key choice is that **everything funnels through SPU register writes**:

```
Song data ──▶ Sequencer / effects engine ──▶ SPU register writes (per tick) ──▶ SPU emulator ──▶ audio
                                                      │
                                                      ├──▶ register log ──▶ .nds ROM player (replays it on hardware)
                                                      └──▶ (WAV/M4A render uses the same path, offline)
SSEQ/SDAT export: a separate converter from song data to Nintendo's event and instrument model
```

Because the sequencer only talks to the SPU through the same registers real hardware has, three things follow:
1. Accuracy is guaranteed by construction: if the emulator can play it, the hardware can too.
2. `.nds` export is cheap. A small player ROM replays the logged register writes on the DS's ARM7, much like VGM files work.
3. The logged register writes can be fed into melonDS as a test oracle.

### Components

| Component | Language | Notes |
| --- | --- | --- |
| `spu-core` | C++ (or C) | The SPU emulator: PSG, noise shift register, PCM8/16, ADPCM decode, mixer, volume divider and pan math, ~32.7 kHz output. No allocations in the render path. Unit tested. |
| `seq-core` | C++ | Song, chain and phrase playback, instruments, tables, grooves and effect commands. Produces register writes each tick. |
| `AudioEngine` | Swift | An `AVAudioSourceNode` pulls from the core at its native ~32,728.5 Hz, and AVAudioEngine resamples to the device rate. A lock-free single-producer/single-consumer ring carries commands from the UI to the audio thread. |
| App UI | SwiftUI | Song, chain, phrase, instrument, table, groove, sample and project screens. Undo and redo. |
| Persistence | Swift | A versioned project format (JSON with sample data in separate files) inside a document package. Files app and iCloud Drive support. |
| Sample tools | C++ / Swift | Import WAV/AIFF, trim, normalize, resample, and **encode IMA-ADPCM** with a size and quality preview. |
| Exporters | Swift + C++ | WAV/M4A, `.nds` builder, SSEQ/SBNK/SWAR/SDAT writer. |
| DS player ROM | C (BlocksDS) | A prebuilt homebrew template. The app patches song data into it. |

### Data model (LSDj-style, adapted to 16 channels)

- **Song:** rows × 16 columns. Each cell holds a chain ID. Columns are tied to specific hardware channels, so PSG instruments are only allowed in columns 8–13 and noise only in 14–15. The UI enforces this.
- **Chain:** up to 16 steps, each a phrase ID plus a transpose.
- **Phrase:** 16 steps, each with a note, an instrument and 1–2 effect commands with values.
- **Instrument:** one of three types.
  - Square (PSG): duty cycle
  - Noise
  - Sample: a sample reference in PCM8, PCM16 or ADPCM, with loop points

  Every instrument also has a volume envelope (ADSR, which maps cleanly to SSEQ), pan, vibrato, finetune and a table.
- **Table:** per-tick automation of volume, pitch, duty cycle and commands, used for arpeggios and drum synthesis.
- **Groove:** a sequence of ticks per step, for tempo and swing.

**Screen layout:** a phone shows 4–8 channel columns at a time and pages through them. An iPad shows all 16. On a folding device, the pattern view goes on top and editing controls on the bottom, reusing the Duo DS layout solver.

## Exports

### 1. WAV / M4A (v1)
An offline render through the same core, shared via the share sheet. Options for loop count and fade-out.

### 2. Playable `.nds` ROM (v1.5)
- The iPhone can't run a compiler toolchain, so we ship a **prebuilt player ROM** built with BlocksDS, the open-source DS homebrew toolchain. It contains a fixed-location data slot or NitroFS file.
- The app writes a compact register log (per-tick deltas plus sample data), patches it into the template, and fixes up the ROM header and CRCs in Swift.
- The player shows song title and artist on the top screen and a live channel visualizer on the bottom.
- **Validation:** run the exported ROM in melonDS, including your Duo DS app, and compare the captured audio with the app's own render. Final check: a real DS with a flashcart.

### 3. SSEQ / SDAT (v2)
- Nintendo's format is event-based, like MIDI, with ADSR instruments (SBNK) and wave archives (SWAR). It **can't express everything a tracker can**, such as per-tick tables or instant duty cycle changes.
- Plan: define a **"SDAT-safe" subset** of effects and instrument features. The app shows a warning icon on anything in a song that won't convert, and the export lists what gets approximated.
- Write the SSEQ, SBNK, SWAR and a minimal SDAT. The ndspy docs and the kiwi.ds SDAT spec are the references.
- **ROM hacking payoff:** replace a track inside a DS game ROM the user dumps themselves. Start with a desktop CLI (Python/ndspy) before adding it to the app. The app never ships or downloads game content.

## Risks and open questions

- **SPU accuracy details.** The exact ADPCM clamping, PSG phase reset on key-on, and mixer rounding are subtle. Mitigation: test against melonDS by running it, and check the final result on real hardware.
- **Licensing.** melonDS is GPL. **Don't copy its SPU code** if you ever want an App Store release, since the GPL conflicts with App Store terms. Write the core from GBATEK and use melonDS only as a black-box oracle in tests. BlocksDS is permissively licensed, which is fine for the player template.
- **Real-time audio in Swift.** Keep the render callback in C++ and avoid Swift allocations and ARC traffic on the audio thread.
- **Tick rate.** The tracker's tick timing needs to map cleanly onto the DS player and SSEQ tempo. SSEQ timing is roughly 192 Hz ticks with 48 ticks per quarter note, and this needs to be verified in Milestone 6 research. Decide the internal tick rate in Milestone 0 with that in mind.
- **SSEQ effect subset.** Exactly which features survive conversion will only be clear after prototyping. It may push the instrument model toward Nintendo's ADSR semantics from the start, which is cheap to do early.
- **Legal.** Use only community documentation and open-source homebrew tools. No Nintendo SDK, BIOS or game assets.
- **Name.** TBD.
